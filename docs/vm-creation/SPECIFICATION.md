# 虚拟机精细创建与部署模板设计方案

状态：设计稿；本轮未修改业务代码、未部署。基于仓库 b929d2f 的 React/TypeScript、Django DRF、Go Agent、libvirt 实现。

## 1. 目标与当前差距

目标：同一创建向导支持快速部署与精细配置，模板用于复用经过验证的配置及约束，最终由后端权限、配额和节点实际能力决定是否可创建。

代码核查：

- `frontend/src/features/vms/VmWizard.tsx` 已有五步向导，但只接入镜像、节点、vCPU、内存、系统盘大小和单网络，没有读取模板，提交时固定 autostart=true。
- `apps/management/apps/templates/models.py` 的 Template 只是规格预设，未包含镜像、设备、初始化或版本。其列表查询尚未按 is_public/created_by 过滤，不能把“私有”标签视作隔离已经实现。
- `apps/management/apps/instances/executors.py` 创建请求未向 Agent 传递镜像源；`services/virt-node-agent/internal/httpapi/domains_create.go` 调用 CreateDisk 新建磁盘，随后定义并启动虚拟机。当前链路未接通选中镜像的克隆或 ISO 挂载。
- `services/virt-node-agent/internal/domainxml/domainxml.go` 当前固定 x86_64、q35、qcow2、virtio 系统盘，只有单盘、单网卡结构。
- autostart 目前进入数据库，但当前创建请求没有把它传给 Agent 设置 libvirt 自启；Agent 无条件调用 StartDomain。必须拆分“立即启动”与“宿主机重启后自启”。
- 当前前端、模板和 Agent 的 CPU/内存上限不一致，应统一为系统策略与节点能力交集。

沿用已有用户、角色、节点 ACL、本人资源范围、个人配额和异步任务。不引入尚不存在的项目/租户授权，也不恢复任何串流或共享工作台功能。

## 2. 产品结构

### 2.1 三种创建入口

1. 快速创建：选择已发布部署模板，填写名称、授权节点及必要参数，其余使用模板默认值。
2. 自定义创建：进入现有五步向导，每步保留常用字段，以折叠区域展示高级配置。
3. 从现有虚拟机保存为模板：后续提供“保存配置模板”，默认不复制磁盘内容；只有通过关机、一致性和身份清理检查的独立流程才能制作黄金镜像。

普通用户默认快速创建，可按权限切换自定义；管理员可管理模板、约束和节点能力。继续使用统一 AppLayout，保留现有页面视觉、导航和间距规范。

### 2.2 五步向导

| 步骤 | 常用配置 | 高级配置及约束 |
| --- | --- | --- |
| 基本信息 | 名称、部署方式、模板版本、操作系统镜像/ISO | 架构、机型、BIOS/UEFI、描述；兼容选项从目标节点能力及镜像元数据筛选 |
| 计算资源 | 授权节点、vCPU、内存 | CPU 模式、插槽/核心/线程；固定绑核、NUMA、hugepages 作为后续管理员能力 |
| 存储 | 系统盘容量、存储池、附加数据盘 | 格式、总线、启动顺序；缓存、discard、I/O 限速由能力及策略决定 |
| 网络 | 一个或多个网络、网卡型号、DHCP | MAC 自动生成；静态 IP、DNS、MTU、带宽限制分期支持；VLAN 来自管理员批准网络 |
| 确认与部署 | 配置摘要、配额变化、节点检查、立即启动、自启开关 | 初始化设置：主机名、用户名、SSH 公钥；显示模板默认值与用户修改项差异 |

右侧摘要在 1440px 下固定适当宽度，1280px 下可折叠；显示资源请求、剩余配额、镜像可用性和校验状态。初始化设置也可从第一步进入独立抽屉，避免最后一步出现未填写的大表单。

切换模板、节点、镜像或固件后，重新校验依赖项；涉及覆盖用户已修改配置时显示差异并确认。高级项不可用时提供原因；默认值应清楚展示，不偷偷降级。

## 3. 配置语义与校验

### 3.1 部署方式

- 云镜像：QCOW2/RAW 镜像生成独立系统盘，校验镜像摘要、格式、架构、所在节点与最小虚拟容量。首期使用独立复制，避免默认引入共享 backing file 删除依赖。
- ISO 安装：新建空系统盘并只读挂载安装介质，明确首次启动顺序；安装完成后可安全卸载。任务完成表示虚拟机及安装介质就绪，不表示操作系统已安装完成。
- 空白虚拟机：仅对具备相应权限的用户开放，明确提示没有可启动系统，不要求提供假的镜像 ID。
- 系统盘扩容与客体分区/文件系统扩容分开描述；只有镜像支持并成功执行初始化扩容时，才能报告客体容量扩展完成。

### 3.2 计算与固件

- sockets × cores × threads = vCPU；vCPU 和内存不得超过节点支持、平台策略及个人剩余配额。
- CPU 模式按节点支持暴露 host-model、host-passthrough 或批准的兼容模型。界面说明兼容模型与迁移限制；不能把 host-passthrough 描述为迁移通用模式。
- 保留当前 q35/x86_64 为旧配置默认值，新架构/机型必须明确实现并验证。
- BIOS/UEFI、Secure Boot、TPM 按节点能力开放。启用 Secure Boot 需同时校验固件及所需密钥配置；TPM 状态和 UEFI NVRAM 属于实例独立资源。
- “创建后立即启动”与“宿主机重启后自动启动”两个独立布尔值，均需 Agent 实际执行并回读验证。平台默认建议立即启动开启、自启关闭；管理员可通过模板显式调整。

### 3.3 磁盘与网络

- 每块盘有稳定设备 ID、角色、存储池、容量、格式、总线和启动序号；不能仅用数组顺序判断系统盘。
- 配额统计系统盘与全部数据盘虚拟容量总和。存储池物理空间、虚拟承诺容量和预留空间分别计算，避免重复扣减；精简分配仍需水位监测。
- 镜像文件只读，创建、清理、恢复不得修改源镜像；存储路径由 Agent 在允许根目录内生成，前端只传资源 ID。
- 每张网卡绑定授权网络 ID，而非任意网桥名称或宿主机接口。MAC 由服务端生成并做唯一性校验。
- 首期 DHCP；静态地址在引入 IP 地址池、租约锁和网络初始化能力后开放。设置 libvirt 接口不等于已配置客体 IP。
- 多网卡静态配置需指定默认路由及优先级，校验同子网冲突、网关、地址占用和 DNS 格式。

### 3.4 初始化与敏感信息

- Linux 云镜像通过 cloud-init NoCloud 初始化；只有镜像声明且验证支持时，才提供对应选项。
- 支持主机名、非 root 用户、SSH 公钥及结构化网络配置。默认不开放任意脚本，管理员脚本功能另需权限、审计和大小/执行策略。
- 普通用户不得通过初始化脚本改变宿主机配置。Windows 初始化单独规划 cloudbase-init/应答文件，不冒用 Linux cloud-init 支持标记。
- 平台模板不保存明文密码、SSH 私钥、固定 MAC、用户令牌或固定租约。需要客体密码时使用受控的加密短期凭证引用；普通任务详情、日志及模板导出均脱敏。
- 初始化成功、失败、超时单独记录。虚拟机已运行而初始化超时时，不删除虚拟机，不宣称系统已就绪，保留诊断入口。

## 4. 模板体系

### 4.1 保留规格模板，增加部署模板

| 类型 | 保存内容 | 用途 |
| --- | --- | --- |
| 规格预设 | CPU、内存、系统盘容量 | 快速调整大小，兼容现有 Template |
| 部署模板 | 镜像引用、硬件、磁盘、网卡、初始化默认值、约束 | 标准化部署操作系统或业务基础环境 |

现有规格预设保持可用，不伪装成包含完整操作系统的模板。部署模板引用已登记镜像，模板本身不重复保存磁盘文件。

建议新增 DeploymentTemplate 与不可变 TemplateVersion，沿用现有 Template 作为规格预设；先明确两者 UI 分区，后续再评估统一目录。

### 4.2 生命周期与可见性

- 生命周期：草稿 → 校验通过 → 发布 → 停用 → 归档；修改已发布模板产生新草稿和新版本，不覆盖旧版本。
- 发布权限与使用权限分开。首期管理员管理平台模板；普通用户使用经授权的已发布版本。个人模板如后续开放，只能由本人及管理员读取。
- 可见性支持平台公开、指定角色、指定用户、私有；公开只表示可见和可申请使用，不授予镜像、节点或创建权限。
- 列表、详情、版本、预校验和创建接口全部执行同一可见性过滤。没有项目模型时不提供项目发布选项。
- 停用阻止新创建，不影响已有虚拟机；已发布版本不能硬删除。镜像被禁用/删除或资源缺失时模板显示不可部署。
- 从实例保存配置时去除资源身份和凭据，保留模板所需约束；制作磁盘镜像需独立任务，不直接保存运行中根盘为通用模板。

### 4.3 默认值和约束

模板字段分别声明默认值、是否可修改、允许值/上下限、是否必填，以及授权镜像/网络/节点候选范围。CPU/内存等数值可设置允许范围，固件/磁盘类型等可设置枚举或锁定值。

处理顺序：读取固定模板版本 → 展开默认配置 → 应用用户允许的覆盖 → 校验模板约束 → 校验当前角色/对象权限 → 校验节点能力、配额和容量。

最终允许范围是模板约束、用户权限和系统/节点能力的交集。模板不能提升用户权限；模板版本被明确固定，模板发布新版不改变历史实例。

示例：Ubuntu 云镜像模板锁定镜像与 virtio 网卡，默认 2 vCPU/4 GiB/40 GiB；允许 CPU 2–8、内存 4–16 GiB、系统盘 40–200 GiB；节点和网络仅从用户当前授权集合中选择。该示例不作为生产固定资源数据。

## 5. 创建与任务流程

1. 读取用户可用模板、镜像、存储、网络和节点能力；所有选项支持分页/检索，不只读取列表第一页。
2. 配置变更后执行前端即时检查，提交前调用后端 preflight。
3. preflight 返回规范化有效配置、字段错误、警告、候选节点、资源增量、模板版本和配置摘要。错误绑定字段路径，如 disks[1].size_gib。
4. 用户确认后，以幂等键提交配置和明确版本。后端重新校验，不把预校验当作容量预留或授权凭证；并发锁定用户配额与目标资源，建立预留。
5. 返回 202 和现有任务引用。worker 持久化步骤检查点：校验 → 镜像准备 → 磁盘准备 → 初始化介质 → 定义实例 → 设置自启 → 按配置启动 → 回读配置/状态。
6. 前端跟踪任务与真实资源状态；网络中断先查询原任务，同一幂等键配不同配置返回冲突。

节点能力探测、Agent 实现能力和平台启用策略必须同时满足才显示功能。探测失败记为未知，普通用户不可选择未经确认的高级项；worker 执行前再检查。预校验响应建议有效期 60 秒，仅用于提示时效。

失败恢复按资源清单和 UUID 判断实际阶段，只清理本任务创建的磁盘、介质、NVRAM/TPM 状态，不删除源镜像或已存在资源。若 Agent 超时导致结果未知，先回查域和磁盘，再决定重试、清理和释放预留。

## 6. 数据与接口建议

主要实体：DeploymentTemplate（名称、所有者、可见性、发布状态）、TemplateVersion（版本号、结构版本、配置、约束、镜像摘要）、InstanceConfig（实例配置快照与来源版本）、InstanceNIC（设备身份及网络）、扩展现有 Disk（池、总线、启动序号）、NodeCapabilities（探测时间、Agent 功能版本及支持项）。

实例始终保存创建时完整配置快照；模板升级不回写实例。配额和节点能力是动态数据，不复制为永久可用承诺。模板引用资源均保留标识和校验摘要，敏感值只保存受控引用。

建议接口均为增量扩展，以下尚未实现：

| 接口 | 用途 |
| --- | --- |
| GET /api/v1/instances/create-options | 授权且兼容的创建选项、能力和策略 |
| POST /api/v1/instances/preflight | 模板解析、配置规范化及创建预校验 |
| POST /api/v1/instances | 扩展现有创建接口，接收结构版本、模板版本及覆盖配置 |
| GET/POST /api/v1/deployment-templates | 部署模板目录与草稿创建 |
| POST /api/v1/deployment-templates/{id}/versions | 新建版本草稿 |
| POST /api/v1/deployment-templates/{id}/versions/{version}/validate | 验证模板完整性及当前可部署性 |
| POST /api/v1/deployment-templates/{id}/versions/{version}/publish | 发布不可变版本 |
| GET /api/v1/nodes/{id}/capabilities | 查询授权节点能力及探测时间 |

旧创建请求映射为 legacy 配置，保持字段语义并补齐真实镜像源；新请求采用版本化嵌套配置。未知字段、未实现能力和锁定字段覆盖均明确拒绝，不能静默忽略。角色权限需增加模板使用、编辑、发布及高级硬件权限，并纳入当前后端权限目录。

主要改动位置：VmWizard、TemplatesPage、前端 API/类型；templates 模型与 API、instances 序列化/服务/执行器、配额与授权；Agent 创建请求、domainxml、storage 和 libvirt 能力探测。现有任务和审计体系继续复用。

## 7. 分期及验收

### 第一阶段：可靠创建与模板复用

- 修复真实云镜像克隆和 ISO 安装链路；拆分立即启动和宿主机自启。
- 在向导接入规格预设，提供管理员管理的版本化部署模板及默认值/锁定约束。
- 实现基本多盘、多网卡，首期使用已验证的存储类型、virtio 设备及 DHCP。
- 引入能力选项、preflight、规范化配置快照、异步任务检查点和失败恢复。

### 第二阶段：初始化与兼容控制

- cloud-init、SSH 公钥、IP 池租约和静态网络、固件/CPU 模式与拓扑。
- 按能力开放 UEFI、Secure Boot、TPM 和必要的 Windows 安装驱动介质。
- 完善模板指定用户/角色可见性、版本差异及配置导出脱敏。

### 第三阶段：性能及设备

- CPU 绑核、NUMA、hugepages、I/O 线程及限速。
- PCI/GPU 直通仅在设备授权、IOMMU 分组、占用锁和回收流程完成后开放。
- 黄金镜像制作、克隆策略与批量创建分别使用专门任务，不通过模板功能隐式引入。

验收必须覆盖：镜像真正可启动或 ISO 真正挂载；模板约束后端不可绕过；旧请求兼容；多盘额度汇总；节点/私有模板越权；模板新版本不影响历史实例；同键同配置只创建一次、异配置冲突；并发不超配额；未知结果回查；失败不删源镜像；固件/多网卡/XML 回读一致；初始化失败状态准确；两个启动开关独立生效；1280×720 下核心操作可用。

## 8. 技术依据

- libvirt 域 XML 支持 CPU、设备和启动配置；实际可用组合需再受节点和平台实现限制：[Domain XML](https://www.libvirt.org/formatdomain.html)。
- libvirt 提供域能力查询，适合作为设备与固件选择依据；缺失项不应被当作已支持：[Domain capabilities](https://www.libvirt.org/formatdomaincaps.html)。
- NoCloud 可通过本地初始化介质提供元数据、用户配置及网络配置，仍要求客体镜像支持相应初始化：[cloud-init NoCloud](https://docs.cloud-init.io/en/latest/reference/datasources/nocloud.html)。
